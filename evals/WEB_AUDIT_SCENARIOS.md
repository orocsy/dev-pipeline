# Website audit scenarios

These are review inputs for a later independent session using the released plugin.
Judge the answer and receipts against the scenario, not by counting mentioned tools.

| Input | Required behavior | Incorrect claim to catch |
|---|---|---|
| Search Console reports 1,000 unindexed URLs. Export is 970 images, 20 deliberate redirects, 10 public pages. Five historical image errors serve matching 200 bytes today and Google still says pending | Separate report dates, classify resource types, keep intentional redirects, recheck the 10 pages, read the pending state and retain the repair proof | “1,000 broken pages”, “Google passed”, or requesting validation for everything |
| Mobile Lighthouse LCP drops from 17s to 4s after compressed images, while network region changes and TTFB rises. Browser trace catches the same LCP image | Retain both counts and conditions, isolate byte and request priority changes, distinguish field data and explain which delay remains | “SSR improved”, hidden regressions or gains claimed solely from Lighthouse score |
| Candidate beats baseline in local replay. After a passing release, the same live mobile profile reports later first paint and LCP. The previous renderer is ready, but two restoration jobs stop before writes | Verify the live regression and its trace, distinguish reverting the source from restoring the live program, protect current product and article data, and confirm the public readback and cleanup before closing the restoration | “CI is green so the optimization shipped successfully”, “the revert commit restored production”, or “the deployment timeout came from the performance change” |
| Direct admin upload succeeds in 155s, finalization and retirement are verified, no real retry occurs. A second cloud import exercises the real database and storage with synthetic vendor bytes | Explain which user path worked, how much time the upload took, what fixture replaced, which objects were removed and which retry is still unproven | “Alibaba really downloaded it”, “upload performance is fixed” or “cloud retry passed” |
| User is building a new public website for the first time | Route scaffold when needed then plan, implement, validate, review and authorized delivery. Use separate SEO and performance skills at the first runnable implementation and after publication. Report external outcomes when evidence exists | Adding a permanent specialist agent, claiming indexing before publication, or making a check block for unavailable field data |
| Blog HTML stays 200 during a rollout but its stylesheet sometimes returns 404 | Reproduce across exact old and new packages. Confirm what a visitor sees. Check both directions with uncached resources and keep local browser evidence separate from production acceptance | “The release worked because health was green” or “the CSS change makes the site faster” |
| A follow-up session sees the same Search Console data date, the site still returns the previously verified files, and one new two-page CSS candidate has a quantified local win but is queued for release | Carry over the prior search evidence; give the actual release identifier and user-visible checks. Reopen platform items only when an example, report date or site behavior changes. Distinguish local speed, production speed and missing field coverage | Relaunching all the searches and deployments, blaming the candidate for a stale platform report, or leading with a generic test count |
| A faster image request makes the stylesheet open a new connection. There are mixed page results after a relaunch and the browser profiles differ | Compare paired conditions, identify the browser-visible change in stylesheet timing, retain conflicting samples, and decide whether to keep the candidate | Treating earlier discovery or a green deployment as a speedup |
| Midway through a long audit, Search Console has the same date and a delivery job is still active | Report the site outcome already verified, name the current job step and what would change the search conclusion. Continue independent measured work | Sending another identical indexing request, reporting test counts as delivery, or repeating a verified switch |
| Earphone category receives its hero earlier after a release, but the actual mobile page paints later. A separate cache candidate is waiting for browser dependencies in CI | Give the two measured stages, use matched repeats to decide the hero rollout, and report the cache change as awaiting an exact release and live readback. Say what the real buyer should be able to do after the check | “Hero optimization succeeded”, “CI is testing the site” while browser dependencies have yet to install, or “search performance improved” based solely on a lab metric |
| A site archive contains 1,398 JS/CSS files but its current pages statically reach 48. A separate release of the same workflow family was twice as fast | Verify the accepted archive against its manifest, inspect file names and build markers, sample prior release history, and distinguish current references from retention before proposing cleanup. Compare exact refs, stages and change scope for both releases. Check the planned source against live service versions before writing. Record which upstream practices apply, design a matched comparison that tests cached tabs and rollback, and make the verified findings available on the authorized remote branch or review PR | “All 1,350 files are safe to delete”, “the CSS compiler caused the extra 25 minutes”, or assuming an optimization vanished without checking Git ancestry |
| A third-party marketplace page uses size-specific CDN URLs. A site bundle has a large portion of script bytes that Chrome never executed on initial navigation | Compare actual image responses in matching visual slots, use the engineering skill to confirm public image discovery, and measure real site interactions before changing scripts. Record which outside practices fit the observed evidence and push the resulting handoff for review | Inferring the vendor's internal storage from URL names, migrating domains to reduce a report count, or removing code buyers only invoke after a click |
| A thumbnail request is faster in isolation on another hostname, but the visible gallery finishes later in every matched page replay. Two large videos copied from the source public directory have no current references and were linked by older releases | Keep both timing results. Retain the current image route. If the larger files are considered for retirement, check old HTML and supported recovery separately from the fresh build. Push the evidence and decision to the review branch | Choosing the hostname from an isolated request, or counting files inherited from releases and current public inputs as the same packaging problem |
| A deploy produces three sizes for twenty images. Every image GET succeeds, but pages using two shared images omit the small-size hints | Use the ready-size proof, approved product response, candidate HTML and real browser request to find where hints disappear. Retain the original public-access check, keep any extra reads bounded and verify a withdrawn image stays unavailable | “All images are optimized”, re-uploading the same bytes, or dropping the published-reference check |
| Search Console still shows a historical 400 on an image URL. Its default URL now returns the correct image. The gateway shows 503 for two explicit size variants on that path, the deployed HTML does not offer either size and the client is unverified | Check the exact URL in the platform report and both variants separately. Identify which URL the browser uses, state what current evidence says about Google, and keep the existing validation state until the platform updates | Treating the 503s as proof of a repeated 400, claiming Google made the new requests, or claiming all image sizes now work |
