# Tenant Data Export — SPEC

> Authored via `dev-pipeline:spec-elicitor` on 2026-07-06.
> This is the contract for downstream phases. Every MIU must trace to a line below.

## 1. Problem Statement (问题陈述)

Salon owners have no self-serve way to get their business data out of the platform.
Today every data-portability or compliance request becomes a support ticket that an
engineer fulfils with a manual SQL dump — slow, error-prone, and a PII-handling risk.
Owners who want their customer/booking data for their own reporting have the same dead
end. Cost of doing nothing: recurring support/engineering toil and compliance exposure
on every request.

## 2. Proposed Solution (方案描述)

A "Data export" section in the admin Settings page. An owner/admin clicks "Request
export"; the export is generated asynchronously; the page shows request status
(pending → processing → ready / failed); when ready, the owner downloads a ZIP
containing one CSV per entity (customers, bookings, services) and also receives an
email with a link back to the download. Extends the existing Settings surface; no new
top-level flow.

## 3. Technical Constraints (技术约束)

- **Apps touched**: api (NestJS), web (Next.js admin surface), Prisma schema
- **Stack constraints**: stay within current stack (NestJS + Prisma + PostgreSQL +
  Redis, Next.js + TanStack Query); no new external services
- **Performance**: export generation is async — no request-path timeout coupling;
  UI status poll is acceptable (no realtime requirement)
- **Multi-tenancy**: every query tenant-scoped; a tenant can NEVER receive another
  tenant's rows; one in-flight export per tenant at a time
- **Locales**: en + zh-HK for all user-facing strings (UI + notification email)
- **Compliance / security**: export contains customer PII — download requires an
  authenticated admin/owner of the owning tenant; artifact + download link expire
  after 7 days; no PII in logs
- **Integration boundaries**: reuses the existing transactional email pathway for
  the "export ready" notification; file storage via the platform's existing
  object-storage abstraction

## 4. Non-goals (明确不做的事)

- End-customer self-service "my data" export — different auth surface and legal
  wording; follow-up round
- Scheduled / recurring exports — one-shot on demand only for now
- Column selection, filtering, or date-range scoping — full-entity dumps only
- Payments / financial data — excluded from the ZIP this round

## 5. Success Criteria (成功标准)

- [ ] An owner/admin can request an export from Settings and see its status change
      pending → processing → ready without leaving the page
- [ ] The downloaded ZIP contains customers.csv, bookings.csv, services.csv with
      correct headers and row counts matching the tenant's data
- [ ] Every row in every CSV belongs to the requesting tenant (verified by a
      cross-tenant isolation test)
- [ ] A second export request while one is pending/processing is rejected with a
      clear message
- [ ] The "export ready" email is delivered and its link leads to a successful
      authenticated download
- [ ] Download attempts after the 7-day expiry are refused (and the UI shows
      "expired")
- [ ] A non-admin staff member can neither request nor download an export

**Data flow**: Settings UI → `POST /exports` → row created PENDING + job enqueued (existing Redis queue infra) → worker: PROCESSING → tenant-scoped reads → CSVs → ZIP → storage → READY(+expiry) → email via `NotificationService` → UI poll sees READY → `GET /exports/:id/download` → short-lived signed URL from `StorageService`.

**Trade-offs considered**
- *Sync streaming download vs async job*: async chosen — large tenants would exceed request timeouts; SPEC explicitly allows polling. Gave up: instant small-tenant exports.
- *One-in-flight enforcement*: partial unique index on `(tenantId) WHERE status IN (PENDING, PROCESSING)` chosen over app-level check — race-proof under concurrent requests (engineering-craft: two concurrent requests could interleave an app-level check).
- *`archiver` (new dep) vs hand-rolled ZIP vs no ZIP (3 links)*: `archiver` — streaming, battle-tested; hand-rolling a binary format is a known footgun; 3 separate links worsens UX and triples signed-URL surface.
- *Signed URL vs proxied stream for download*: signed URL via existing `StorageService.getSignedUrl` — keeps large payloads off the API; auth still enforced by the endpoint that mints it.
