## STEP 3: Fix

**Decision — revert, don't fix forward.** Restoring known-good behaviour is the hotfix
contract (Rule 23 exemption text: "production-down = restore known-good behaviour"). A forward
fix (re-adding defaults key-by-key) re-litigates the refactor's design under incident pressure.
`git revert` (NOT `git reset --hard` — shared history is never rewritten) touches the minimum
surface and is class-level by construction.

**Rule 11 (fix the class, not the instance):** the class is "all four keys converted to
`getOrThrow`", not just `CORS_ORIGINS`. Checked all four against the production environment
(`gh api` on the repo's prod environment secrets/vars + deploy workflow env block):
`CORS_ORIGINS` and `TRUST_PROXY` are missing in prod; `RATE_LIMIT_MAX` and `REQUEST_LOG_LEVEL`
happen to be set. A one-key patch would have left a second landmine — the revert covers the
whole class. ✅ enumerated, covered.

**Rule 12 note (simpler fix one layer up?):** considered setting the two missing prod env vars
instead of touching code. Rejected for the incident: it leaves per-request `getOrThrow` as a
standing failure mode (any future env drift = full outage again) and prod config mutation is
slower to verify than shipping the known-good code path. The env-schema/boot-validation version
of that layer-up fix is scheduled as the follow-up reland (below), not smuggled into the hotfix
(hotfix.md: "No refactoring. No while-I'm-here improvements.").

> **Bash** `git checkout -b hotfix/config-getorthrow-500`  *(branch first — never commit direct to main)*

> The new regression test from STEP 2 is kept (Rule 19 pattern 1: new test for the invariant
