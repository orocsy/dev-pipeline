# Customer CSV Import — SPEC

## 1. Problem Statement (问题陈述)

Salon owners arriving from a previous booking tool or a spreadsheet have no way
to bring their existing customer base into the platform. Today small salons
hand-type customers one at a time (onboarding stalls; some never finish) and
large salons escalate to support, who run ad-hoc database inserts per salon.
Two trials churned last quarter citing "no way to bring our customers over".
Cost of doing nothing: stalled onboarding, recurring support load, and lost
trials.

## 2. Proposed Solution (方案描述)

An "Import CSV" action on the admin Customers page. The owner downloads a fixed
4-column template (`name, phone, email, notes` — name+phone required), uploads
their file, and gets a **validation preview**: how many rows will import, which
rows match an existing customer (matched by normalized phone first, then email)
and will be skipped, and which rows are invalid — each itemized with row number
and reason. The owner confirms; valid rows import; a summary is shown.
Duplicates inside the file resolve first-occurrence-wins. ◇ Phone matching uses
the same E.164 normalization as regular customer creation, so "6123 4567" and
"+852 6123 4567" are the same customer. ◇ A row matching a soft-deleted
customer restores that customer (undeletes and updates fields from the CSV) and
is reported in its own "restored" category.

## 3. Technical Constraints (技术约束)

- **Apps touched**: api (new import endpoint/service, new table), web
  (Customers page import dialog)
- **Stack constraints**: stay within current stack (NestJS, Prisma, Next.js); a
  CSV-parsing dependency is acceptable if verified — never hand-rolled parsing
- **File cap**: ≤ 5,000 rows and ≤ 5 MB per file; processing is synchronous
- **Multi-tenancy**: every imported row is scoped to the importing salon's
  tenant, derived from the authenticated admin context — never from the file.
  A file carrying tenant-identifying columns is rejected as invalid. [Blindspot §7]
- **Auth**: OWNER and ADMIN roles only; STAFF may not import. [Blindspot §7]
- **Locales**: en + zh-HK — every dialog string AND every per-row error-report
  string via translation keys in both message files. [Blindspot §7]
- **Compliance / security (PII)**: the preview/error report carries row number
  + field name + reason only; raw cell values (names/phones/emails) never
  appear in server logs. [Blindspot §7]
- **Data / migrations**: one new table for the per-import summary record
  (who, when, file name, counts). Additive migration only; no backfill. [Blindspot §7]
- ◇ **Plan-tier cap**: imports respect the per-plan customer limit enforced by
  the entitlement layer; an import that would exceed the importing salon's cap
  is rejected before commit with the cap details. [Blindspot §7, stage 2]
- ◇ **Concurrency**: the commit phase runs under a per-tenant lock (same
  two-layer pattern as booking mutations) so two simultaneous imports cannot
  interleave dedupe checks. [Blindspot §7, stage 2]
- **Integration boundaries**: none — no external APIs.

## 4. Non-goals (明确不做的事)

- Excel/.xlsx input — CSV only; the template keeps the contract testable
- Flexible column mapping — fixed template this round; mapping wizard is a follow-up
- Duplicate field-merging/updating — duplicates are skipped and reported, never mutated
- Background/async import jobs — synchronous within the 5k/5 MB cap (see §6)
- Customer export (the reverse direction) — separate feature, separate SPEC
- Notifications to imported customers — no welcome/consent email or SMS of any
  kind this round [Blindspot §7]
- ◇ Per-row `customer.created` side effects — the import emits ONE
  `customers.imported` event with counts; no per-row created events, and
  imported customers do NOT receive loyalty welcome points [Blindspot §7, stage 2]

## 5. Success Criteria (成功标准)

- [ ] Owner uploads a template CSV → preview counts (importable / duplicate /

- [ ] Every skipped, restored, or errored row is itemized with row number and

- [ ] Duplicates match by normalized phone first, then email; in-file

- [ ] A salon's import can never create, modify, or read another salon's
      customers (tenant isolation proven by test)
- [ ] STAFF-role users receive 403 from the import endpoint (proven by test)
- [ ] ◇ An import that would exceed the salon's plan-tier customer cap is
      rejected before any row is written, with the cap surfaced to the user

## 6. Quality Criteria (质量标准)

- [ ] Perf budget: a 5,000-row file previews in < 10s and commits in < 10s

- [ ] Import endpoint rate-limited to 3 imports per hour per tenant [Blindspot §7]
- [ ] Every import (preview excluded, commit only) persists a summary record

## PHASE 4 — Technical Design

→ Invoking `@writing-plans` (structured decomposition methodology loaded)
→ Launching Agent: **technical-architect** (inputs: SPEC + addenda, CLAUDE.md rules, 11 key files, Phase 2 skill list)

**Architecture (decisive single choice):**

- **Pattern precedent:** extend the existing `customer` module (`apps/api/src/modules/customer/`) rather than a new top-level module — the import is a customer-domain write path and reuses `normalizePhone` (`customer.service.ts:41`) and the module's guards. Concurrency follows `booking.service.ts:112` (redis lock + serializable tx).
- **Endpoint — ONE route, two-phase stateless:** `POST /v1/customers/import` (multipart: `file` + `mode: 'preview' | 'commit'`). Preview parses + validates + dedupe-checks + cap-checks and returns the report with **zero writes**; commit re-uploads the same file and re-runs the full validation inside the lock + transaction before writing. Stateless beats holding parsed files across requests (no session storage, no expiry bugs); the 5 MB cap makes the re-upload cost trivial.
- **Backend components** (all under `apps/api/src/modules/customer/import/`):
  - `import-customers.dto.ts` — `ImportCustomersDto { mode: 'preview' | 'commit' }` (`@IsEnum`; `forbidNonWhitelisted` rejects stray form fields by design) + `ImportReportDto { totalRows, importable, duplicates[], restored[], errors[], capExceeded? }` with row entries `{ row: number; field?: string; reasonKey: string }` — **`reasonKey` is a translation key enum, never English prose** (SPEC §3 i18n; analyst B's flag).
  - `csv-customer-row.parser.ts` — `csv-parse` wrapper: `columns: true` with case-insensitive header validation against the fixed template, `bom: true`, `skip_empty_lines: true`, strict column count, 5,000-row + 5 MB guards, UTF-8-only (invalid byte sequences → file-level `reasonKey: 'import.errors.encoding'`), tenant-ish header names (`tenant`, `salon`, `tenantId`…) → file-level rejection (SPEC §3). Reuses `normalizePhone`; rejects notes > 500 chars per row. **Raw cell values never passed to the logger** (SPEC §3 PII).
  - `customer-import.service.ts` — orchestrates preview/commit. Dedupe: in-file first-wins map by normalized phone → existing lookup `WHERE tenantId AND (phone IN … OR email IN …)` including soft-deleted; cap check via `entitlement.service.ts` (`currentActive + toImport + toRestore ≤ CUSTOMER_LIMIT`, else `capExceeded` report, 422 on commit). Commit: redis lock `lock:customer-import:{tenantId}` (booking pattern, 30s TTL) → serializable tx → re-validate → `createMany` in chunks of 500 + `updateMany` restores → persist `CustomerImport` record → `audit.log(actor, 'customers.import', {tenantId, counts})` → emit ONE `customers.imported` event (no per-row `CustomerCreatedEvent` — SPEC §4).
  - `customer-import.controller.ts` — `FileInterceptor('file', { limits: { fileSize: 5 * 1024 * 1024 }, fileFilter: csv-only })`, `JwtAuthGuard + RolesGuard @Roles('OWNER','ADMIN')`, tenant via `@TenantId()` only, `@Throttle({ default: { limit: 3, ttl: 3_600_000 } })` on the existing tenant-keyed `TenantThrottlerGuard` — **commit only**; preview shares the route but throttling counts both (conservative, stated trade-off).
- **Data model:** new `CustomerImport` model — `{ id, tenantId, actorId, fileName, totalRows, importedCount, skippedCount, restoredCount, errorCount, createdAt }`, `@@index([tenantId, createdAt])`. Additive migration, no backfill (SPEC §3).
- **Frontend:** `importCustomers(file, mode)` in `apps/web/src/lib/api/customer-import.ts` (FormData per `media.ts:12` precedent, typed against `ImportReportDto`); `ImportCustomersModal` client component (Modal + FileUpload + report Table + template download link to `public/templates/customer-import-template.csv`; states idle → uploading → preview → committing → done/error; all strings + all `reasonKey`s via `useTranslations('customers.import')` in en + zh-HK).
- **Trade-offs:** two-phase stateless re-upload over stored parse (simplicity, SPEC §6); reject-over-cap over partial-import-to-cap (user's F1 decision — predictable accountant-grade behaviour); `csv-parse` over hand-rolled splitting (engineering-craft library-choice: RFC 4180 edge cases — embedded quotes/newlines/BOM); one route with `mode` over two routes (single guard/throttle/interceptor surface).

**Third-Party Surfaces Verified (Rule 22):**

| Library/Service | Behavior depended on | Evidence | Installed? |
|---|---|---|---|
| `csv-parse` (NEW dep) | `parse(input, { columns, bom, skip_empty_lines, relax_column_count: false })` sync + streaming API; per-record `info.lines` for row numbers; throws `CsvError` with `code` | context7 `resolve-library-id` → `query-docs` (options + error API). Not yet installed → recorded in `docs/customer-csv-import/SDK-PROBE.md`; re-verify against installed `.d.ts` at MIU 2 (Phase 7.6 re-checks mechanically) | no |
